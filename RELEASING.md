# Preparing an EquWord release

Keep the working repository outside Dropbox, such as `~/Published_Software/EquWord` on Mac or `%USERPROFILE%\Published_Software\EquWord` on Windows. From its top-level folder, run `python scripts/start_work.py` before making changes. Review the resulting working state before editing.

1. Complete native Word tests for the exact candidate on the intended Mac and Windows builds. Record the version, binary SHA-256 and honest test scope. Keep private test logs, manuscript files and separate VBA exports outside the public package.
2. Update the seven files in `package/` as appropriate. Keep the root and package `CITATION.cff` identical, and the two `LICENSE.txt` files identical. Update `CHANGELOG.md` and the README when the version or tested scope changes. After native tests pass, deliberately update `RELEASE_MANIFEST.json` with the accepted version, exact file sizes/hashes and brief test summary. The builder verifies this evidence and never regenerates or approves it.
3. Run `python scripts/build_release.py --output-dir <absolute-new-directory>`. It verifies the manifest and creates `EquWord.zip` and `EquWord.zip.sha256` in the chosen output directory (the default is ignored `dist/`). The archive uses the contents of `package/` as its root and preserves the `Tutorial/` subfolder, with a fixed timestamp and reproducible stored ZIP entries. `dist/` is ignored by Git. A different existing asset is never overwritten; move to a new output folder using `--output-dir` followed by an absolute path. `--verify-only` performs the checks without writing output.
4. Review the changes, commit them and push the intended commit. Create a **draft** GitHub release for that commit and the chosen version tag. Attach `EquWord.zip` and its checksum; inspect the download contents and release description before publication. Keep the stable asset name `EquWord.zip` for each version.
5. **Before publishing the first release**, link the GitHub account in Zenodo and enable `PsycheMatrica/EquWord` on Zenodo's GitHub page. [Zenodo's repository-enabling guide](https://help.zenodo.org/docs/github/enable-repository/) explains this setup. Use `CITATION.cff` as the metadata source; do not add a competing `.zenodo.json`. No GitHub Actions workflow is needed for Zenodo's native integration.
6. Show the exact version, target commit, ZIP filenames/checksums, release notes and verification results to Gyeongcheol Cho. **Obtain his explicit final confirmation for this prepared release.** Initial instructions to prepare a release or connect Zenodo do not authorize publication. Keep the draft unpublished until that confirmation arrives. Repeat this final review for every release.
7. Publish the confirmed GitHub release only after that final approval and after the repository is enabled in Zenodo. Then wait for [Zenodo's release processing](https://help.zenodo.org/docs/github/archive-software/github-upload/) and inspect its result.
8. Verify the actual DOI, title, author, version, license and archived file contents. Check which archive Zenodo preserved: a repository/tag archive can have a different wrapper and additional repository files compared with the downloadable `EquWord.zip`. Do not assume that the GitHub release asset itself was archived. If the intended package is missing, resolve that in Zenodo before advertising the record as the package archive. Add the confirmed DOI and publication date to the citation metadata and remove preparation-status wording only after publication actually occurred. Preserve the released asset and checksum; document subsequent changes for the next version.

The 1.0.0 candidate changes the template's internal version display as explicitly requested. Its visible executable source must differ from 0.9.27 V5 only in the version constant; the version comment can also be updated. Record its new exact SHA-256. Native Word rebuilding regenerated form identity metadata and canonicalized a default background property; retain the strict byte-audit qualification and supplementary review, and test form loading, events and saved choices on both platforms. Earlier V5 tests are not a runtime pass for this new binary.

The schema 2 manifest separates candidate byte identity from native platform evidence. A draft can be built while a platform is pending. Before final review, run `python scripts/build_release.py --publication-check --verify-only`; this refuses a candidate unless both Mac and Windows report PASS for the exact candidate version/hash and identify their evidence. Passing this check never authorizes publication.

Zenodo's GitHub integration cannot pre-reserve a DOI. Do not create an unrelated manual upload in an attempt to preassign this automated record. First prepare and review 1.0.0 without a DOI, then publish only with the user's final approval. Verify the actual version and Concept DOIs. Add them to current main-branch citation/README/website metadata. Preserve the released tag and asset bytes; a subsequent guide file update needs a clearly identified document revision or later release. The GitHub integration archives the repository snapshot, so all seven distribution members must be tracked at the release commit.
