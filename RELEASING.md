# Preparing an EquWord release

Keep the working repository outside Dropbox, such as `~/Published_Software/EquWord` on Mac or `%USERPROFILE%\Published_Software\EquWord` on Windows. From its top-level folder, run `python scripts/start_work.py` before making changes. Review the resulting working state before editing.

1. Complete native Word tests for the exact candidate on the intended Mac and Windows builds. Record the version, binary SHA-256 and honest test scope. Keep private test logs, manuscript files and separate VBA exports outside the public package.
2. Update the six files in `package/` as appropriate. Keep the root and package `CITATION.cff` identical, and the two `LICENSE.txt` files identical. Update `CHANGELOG.md` and the README when the version or tested scope changes. After native tests pass, deliberately update `RELEASE_MANIFEST.json` with the accepted version, exact file sizes/hashes and brief test summary. The builder verifies this evidence and never regenerates or approves it.
3. Run `python scripts/build_release.py`. It verifies the manifest and creates `dist/EquWord.zip` and `dist/EquWord.zip.sha256`. The archive contains the six package files at its root, with a fixed timestamp and reproducible stored ZIP entries. `dist/` is ignored by Git. A different existing asset is never overwritten; move to a new output folder using `--output-dir` followed by an absolute path. `--verify-only` performs the checks without writing output.
4. Review the changes, commit them and push the intended commit. Create a **draft** GitHub release for that commit and the chosen version tag. Attach `EquWord.zip` and its checksum; inspect the download contents and release description before publication. Keep the stable asset name `EquWord.zip` for each version.
5. **Before publishing the first release**, link the GitHub account in Zenodo and enable `PsycheMatrica/EquWord` on Zenodo's GitHub page. [Zenodo's repository-enabling guide](https://help.zenodo.org/docs/github/enable-repository/) explains this setup. Use `CITATION.cff` as the metadata source; do not add a competing `.zenodo.json`. No GitHub Actions workflow is needed for Zenodo's native integration.
6. Publish the reviewed GitHub release only after the repository is enabled in Zenodo. Then wait for [Zenodo's release processing](https://help.zenodo.org/docs/github/archive-software/github-upload/) and inspect its result.
7. Verify the actual DOI, title, author, version, license and archived file contents. Check which archive Zenodo preserved: a repository/tag archive can have a different wrapper and additional repository files compared with the downloadable `EquWord.zip`. Do not assume that the GitHub release asset itself was archived. If the intended package is missing, resolve that in Zenodo before advertising the record as the package archive. Add the confirmed DOI and publication date to the citation metadata and remove preparation-status wording only after publication actually occurred. Preserve the released asset and checksum; document subsequent changes for the next version.

The current 0.9.27 manifest identifies the already tested V5 binary. Documentation or branding edits do not authorize changing that binary or broadening its recorded test claims.
