# Preparing an EquWord release

Work in the actual public checkout outside Dropbox after reading `AGENTS.md`, preserving existing changes and running the clean-checkout start helper. A local promotion preview is separate from that checkout and does not authorize promotion, committing, pushing or publishing.

1. Identify the exact software candidate and record honest native test scope. The current `EquWord.dotm` SHA-256 is `3e876985b016db8e0bb242b57a2036aeb80ebc720201410e0e32698ece583a13`. Read the candidate-specific platform entries and limitations in `RELEASE_MANIFEST.json`. Earlier tests do not establish a runtime pass for different bytes.
2. Review the seven `package/` members. Keep root/package citation files identical and root/package licenses identical. Use `EquWord.dotm` and `Tutorial/EquWord_Practice.docx`; do not keep duplicate legacy template/practice names in the package. Transfer approved public files only, not a complete private handoff folder.
3. Deliberately update the schema 2 member hashes, archive identity and recorded native evidence. Public metadata contains sanitized scope and evidence hashes, not private paths or raw logs. A PASS describes the recorded scope; it does not assert exhaustive testing. Preserve the Mac full-log saving limitation and unverified full-regression scope.
4. Run `python scripts/build_release.py --verify-only` and `python scripts/build_release.py --publication-check --verify-only`. These check bytes and declared readiness; they do not execute Word or authorize publication. The current seven-member archive uses sorted names, DEFLATED compression level 6, fixed entry timestamp 2026-10-28 00:00:00, Unix creator and mode 100644. Its deliberately recorded SHA-256 is `7445ce7810992905ba826db6540eb87f57aa32d1e3b80303e50bff989e97d98d`.
5. Build with `python scripts/build_release.py --output-dir <absolute-new-directory>`. Default output is ignored `dist/`. Use a new output directory when different assets already exist. The helper refuses to overwrite different bytes and refuses an archive that differs from the recorded identity. Preserve the existing reviewed/released asset if a platform or compression runtime produces a different digest; investigate before changing accepted hashes.
6. Inspect the actual diff and staged public files. Commit and push only under the authorized repository-work scope. Select the intended commit for a draft release; inspect the ZIP, sidecar and notes. Do not publish it yet.
7. Verify the author's existing Zenodo account connection and the EquWord repository setting before the first publication. Do not create a new account or an unrelated upload to invent a DOI. The native GitHub integration uses release events; `CITATION.cff` is the metadata source. No competing `.zenodo.json` is required.
8. Present the exact version, target commit, filenames/checksums, notes and actual Windows/Mac verification scope to the author. Obtain explicit final confirmation for this concrete release. Preparation instructions, account access and ordinary commit/push authorization are not release approval. This step applies to every release.
9. Publish only the approved release. Verify Zenodo's actual resulting DOI, title, author, version, license and contents. A repository/tag archive can differ from the downloadable package ZIP; check what was archived rather than assuming the release asset was preserved.
10. Add verified version/Concept DOI and publication metadata only after publication occurred. Preserve released tag and asset bytes. Later guide revisions require an identified revision or subsequent release, not silent replacement.
